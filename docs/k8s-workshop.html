Kubernetes ฉบับลงมือ ตั้งแต่ติดตั้งถึง deploy

เริ่มจากเครื่องเปล่า ลงเครื่องมือ สร้าง cluster จำลอง EKS บนเครื่องตัวเอง build image แล้ว deploy ขึ้นเอง จากนั้นส่อง cluster, ลองทำ pod พังแล้วดูมันซ่อมตัวเอง, แก้ ConfigMap, ออก version ใหม่โดย user ไม่เห็น error และหาสาเหตุเวลา pod พัง

จบแล้วทำได้
  • ตั้ง cluster, build image และ deploy app ขึ้น k8s ได้เอง
  • อ่าน get / describe / logs แล้วบอกได้ว่า pod เป็นอะไร
  • อธิบายได้ว่าแก้ ConfigMap แล้วทำไมบางค่าเปลี่ยนเลย บางค่าต้อง restart
  • รู้ว่า k8s ซ่อมตัวเองยังไง และ deploy ยังไงไม่ให้ระบบล่ม

แนวคิดหลัก

เราบอก k8s ว่า อยากได้อะไร (desired state) แล้ว k8s เทียบกับของจริงและแก้ให้ตรงอยู่ตลอดเวลา เราไม่ได้สั่งทีละขั้น

Pod

กล่องที่ app รันอยู่จริง ตายได้ ถูกแทนที่ได้ ชื่อเปลี่ยนทุกครั้งที่เกิดใหม่

Deployment

ใบสั่งว่า "อยากได้ pod แบบนี้ 2 ตัว" k8s คอยดูแลให้มีครบเสมอ

Service

ชื่อและ IP ที่คงที่อยู่หน้า pod หลายตัว คอยกระจาย request ให้

ConfigMap

ค่า config ที่แยกจาก image เปลี่ยน config ได้โดยไม่ต้อง build ใหม่

จากโค้ดถึง user
โค้ด→docker build→registry (เหมือน ECR)→kubectl apply→Pod
curl→LB (เหมือน NLB)→Ingress→Service→Pod←ConfigMap
ผู้สอน: วาด 2 เส้นนี้บนกระดาน ภารกิจ 1–4 เดินตามเส้นบน ภารกิจ 5–9 อยู่บนเส้นล่าง บอกน้องว่า worker 3 ตัวคือ 3 AZ ของ ap-southeast-1 เหมือน EKS ที่บริษัทใช้

สร้าง cluster

ได้ k8s 4 node (control-plane 1 + worker 3) บนเครื่องตัวเอง

ทางลัด

make up ทำขั้น 1 และรอจนขั้น 3–4 เสร็จให้ในคำสั่งเดียว วันนี้พิมพ์เองเพื่อให้เห็นว่ามีอะไรเกิดขึ้น

  1. เปิด cluster 
    mkdir -p .kube
docker compose up -d
docker compose ps

    ได้ container 6 ตัว: control-plane, worker-1a/1b/1c, lb (ทำหน้าที่เหมือน NLB) และ registry (เหมือน ECR) ข้างในแต่ละ node รัน k3s ซึ่งเป็น Kubernetes จริงที่ผ่าน certification ของ CNCF

  2. ตั้งค่า terminal (ทำทั้ง 2 จอ) 
    export KUBECONFIG=$PWD/.kube/kubeconfig.yaml
alias k=kubectl
S=nest-lab-staging
STG=http://staging.nest-lab.localhost:8080

    KUBECONFIG บอก kubectl ว่าคุยกับ cluster ไหน ไฟล์นี้อยู่ในโปรเจกต์ จึงไม่ไปยุ่งกับ ~/.kube/config ที่อาจชี้ไป cluster ของบริษัท

  3. รอ node พร้อม 
    k get nodes -w

    รอจน 4 node เป็น Ready (ประมาณ 30–60 วินาที) แล้วกด Ctrl-C ถ้าเจอ connection refused หรือหาไฟล์ kubeconfig ไม่เจอ แปลว่า control-plane ยัง start ไม่เสร็จ รอ 10–20 วินาทีแล้วลองใหม่

  4. ดู system pod 
    k -n kube-system get pod

    รอ coredns (DNS ใน cluster), traefik (Ingress) และ metrics-server (ใช้กับ HPA) เป็น Running. pod ชื่อ helm-install-* ขึ้น Completed เป็นเรื่องปกติ

Build และ push image

แปลงโค้ดเป็น image แล้วเอาขึ้น registry ให้ cluster ดึงไปใช้ได้

ทางลัด

make image = ขั้น 2 + 3

  1. อ่าน Dockerfile ด้วยกัน 
    cat Dockerfile

    ชี้ 3 จุด: แยก 2 stage (stage แรก build TypeScript, stage หลังเก็บแค่ dist กับ dependency ที่ใช้ตอนรัน image จึงเล็ก), USER 1000:1000 ไม่รันเป็น root และ APP_VERSION ที่ฝัง version ไว้ใน image

  2. build 
    docker build --build-arg APP_VERSION=0.1.0 -t localhost:5001/nest-lab:0.1.0 .
docker images localhost:5001/nest-lab

  3. push แล้วเช็กว่าขึ้นจริง 
    docker push localhost:5001/nest-lab:0.1.0
curl -s localhost:5001/v2/nest-lab/tags/list
    ควรเห็น

Deploy ขึ้น k8s

apply manifest แล้วเรียก app ได้ผ่าน LB

CreateContainerConfigError
ทางลัด

make deploy สร้าง Secret ก่อนแล้วค่อย apply จึงไม่เห็น error ในขั้น 3 วันนี้เราจะลืมสร้าง Secret โดยตั้งใจ

  1. ดูว่าจะ deploy อะไรบ้าง 
    ls k8s/base k8s/overlays/staging
k kustomize k8s/overlays/staging | grep '^kind:'
    ควรเห็น
    kind: Namespace
kind: ServiceAccount
kind: ConfigMap
kind: ConfigMap
kind: Service
kind: Deployment
kind: PodDisruptionBudget
kind: HorizontalPodAutoscaler
kind: Ingress
kind: NetworkPolicy
kind: NetworkPolicy

    base คือของที่เหมือนกันทุก environment ส่วน overlays/staging แก้เฉพาะที่ต่าง เช่น namespace, จำนวน replica, ค่า config. production ใช้ base เดียวกันแต่คนละ overlay

  2. apply 
    k apply -k k8s/overlays/staging

    จะเห็น created 11 บรรทัด ถ้ารันซ้ำจะขึ้น unchanged เพราะ apply บอกแค่ว่าอยากได้อะไร ไม่ได้สั่งสร้างใหม่

  3. ดู pod แล้วหาว่าทำไมไม่ขึ้น 
    k -n $S get pod
k -n $S get events --field-selector reason=Failed
    ควรเห็น
    nest-lab-xxxx   0/1   CreateContainerConfigError
...  Error: secret "nest-lab-secret" not found

    Deployment อ้างถึง Secret ชื่อ nest-lab-secret ที่ยังไม่มี เราไม่ใส่ Secret ไว้ใน manifest เพราะ manifest อยู่ใน git

  4. สร้าง Secret แล้วดู pod ขึ้นเอง 
    k -n $S create secret generic nest-lab-secret --from-literal=API_KEY=lab-staging-api-key-change-me
k -n $S get pod -w

    ไม่ต้อง apply ใหม่ kubelet ลองซ้ำเรื่อย ๆ พอเจอ Secret ก็ start ได้เอง (ตอนทดสอบ lab นี้ใช้ไม่ถึง 30 วินาที) บน EKS จริงเก็บ Secret ใน AWS Secrets Manager แล้วใช้ External Secrets Operator สร้าง Secret ให้

  5. เรียก app ผ่าน LB 
    k -n $S rollout status deploy/nest-lab
curl -s $STG/ | jq
    ควรเห็น
    "env": "staging",
"message": "Hello from STAGING",

    *.localhost ชี้มาที่เครื่องตัวเองอยู่แล้ว ไม่ต้องแก้ /etc/hosts

พัก 10 นาที ใครยังไม่ถึงภารกิจ 4 ให้ใช้ช่วงนี้ตามให้ทัน หรือรัน make up && make image && make deploy แล้วตั้งค่า terminal ตามภารกิจ 2 ขั้น 2. เครื่องไหน sleep ไปแล้วเจอ Unauthorized หรือ rollout ค้าง ให้รัน make stop && make start

ส่อง cluster

รู้ว่ามี node อะไร app อยู่ตรงไหน และเรียก app ได้

Running
  1. ดู node และ zone 
    k get nodes -L topology.kubernetes.io/zone
    ควรเห็น
    NAME            STATUS   ROLES           ZONE
control-plane   Ready    control-plane
worker-1a       Ready    <none>          ap-southeast-1a
worker-1b       Ready    <none>          ap-southeast-1b
worker-1c       Ready    <none>          ap-southeast-1c

    control-plane ไม่รับ app เพราะติด taint เหมือน EKS ที่ AWS ดูแล control plane ให้ เราเห็นแค่ worker

  2. ดู app ที่ deploy ไว้ 
    k -n $S get deploy,pod,svc -o wide

    ดู 3 คอลัมน์: READY 1/1, STATUS Running, NODE (pod 2 ตัวควรอยู่คนละ node)

  3. เรียก app แล้วดูว่า pod ไหนตอบ 
    curl -s $STG/ | jq
for i in 1 2 3 4 5 6; do curl -s $STG/ | jq -r .pod.name; done

    ชื่อ pod สลับกันไปมา แปลว่า Service กระจาย request ให้ทุก pod

  4. อ่านรายละเอียดของ Deployment 
    k -n $S describe deploy nest-lab

    ให้น้องหา 4 อย่าง: จำนวน replicas, image, บรรทัด Liveness/Readiness และ ConfigMap ที่ใช้ (Environment Variables from)

  5. อ่าน log 
    k -n $S logs deploy/nest-lab --tail=5

    log เป็น JSON บรรทัดละ event เพราะ production ส่ง log เข้า CloudWatch/Datadog ซึ่งอ่าน JSON ได้ง่าย

ภารกิจ 6 · 15 นาที

พังแล้วดูมันซ่อม

เห็นกับตาว่า k8s ซ่อมตัวเองได้ 3 แบบ

ContainerCreating
จอ 2 เปิดค้างไว้
k -n $S get pod -w
  1. ลบ pod ทิ้ง 1 ตัว 
    k -n $S delete $(k -n $S get pod -l app.kubernetes.io/name=nest-lab -o name | head -1)

    จอ 2 เห็น pod ชื่อใหม่ขึ้นมา ContainerCreating แล้วเป็น Running เพราะ Deployment อยากได้ 2 ตัว พอเหลือ 1 ก็สร้างเพิ่มให้

  2. ทำให้ process ใน pod ตาย 
    curl -s -X POST $STG/chaos/crash
k -n $S get pod

    รอบนี้ชื่อ pod เดิม แต่ RESTARTS เพิ่มเป็น 1 เพราะ container ตายแต่ pod ไม่หาย kubelet จึง restart container ใน pod เดิม

  3. อ่าน log ของรอบที่ตาย 
    k -n $S logs <ชื่อ-pod-ที่-RESTARTS-1> --previous --tail=3

    --previous คือ log ของ container ตัวก่อนหน้าที่ตายไปแล้ว ถ้าไม่ใส่จะเห็นแค่ log ของตัวใหม่ที่ยังไม่มีอะไร

  4. ทำให้ pod "ไม่พร้อม" แต่ยังไม่ตาย 
    curl -s -X POST "$STG/chaos/ready?state=false"
k -n $S get pod
for i in 1 2 3 4 5 6; do curl -s $STG/ | jq -r .pod.name; done

    pod นั้นเป็น READY 0/1 แต่ไม่ถูก restart และไม่ได้รับ request อีกแล้ว ชื่อที่ตอบกลับมาเหลือชื่อเดียว

  5. เอากลับมาปกติ 
    k -n $S rollout restart deploy/nest-lab
k -n $S rollout status deploy/nest-lab
  6. probe ที่ failk8s ทำอะไรใช้ตอนไหน
    livenessrestart containerapp ค้าง ตอบไม่ได้แล้ว
    readinessเอาออกจาก Service ชั่วคราว ไม่ restartapp ยังไม่พร้อม เช่นกำลัง start หรือ DB หลุดชั่วคราว

    /chaos/* เปิดเฉพาะ staging ถ้าเรียกที่ production จะได้ 404

ConfigMap 2 แบบ

แก้ config แล้วดูว่าแบบไหนเห็นผลทันที แบบไหนต้อง restart

ConfigMapเข้า app ทางแก้แล้ว
nest-lab-envenv varต้อง restart
nest-lab-filesไฟล์เปลี่ยนเองใน ~1 นาที
  1. ดู ConfigMap ทั้งสองตัว 
    k -n $S get cm
k -n $S get cm nest-lab-env -o yaml
curl -s $STG/config | jq

    /config โชว์ค่าจากทั้ง 2 ทาง: fromEnv และ fromFile

  2. แก้ค่าแบบ env 
    k -n $S patch cm nest-lab-env --type merge -p '{"data":{"GREETING":"Hello from team junior"}}'
curl -s $STG/ | jq .message
    ควรเห็น (ยังเป็นค่าเก่า)
    "Hello from STAGING"

    ให้น้องเดาก่อนว่าทำไมยังไม่เปลี่ยน

  3. restart แล้วดูอีกที 
    k -n $S rollout restart deploy/nest-lab
k -n $S rollout status deploy/nest-lab
curl -s $STG/ | jq .message
    ควรเห็น
    "Hello from team junior"

    env var ถูกอ่านแค่ครั้งเดียวตอน process เริ่ม แก้ ConfigMap อย่างเดียวจึงไม่พอ ต้องมี pod ใหม่

  4. แก้ค่าแบบไฟล์ แล้วดูมันเปลี่ยนเอง 
    k -n $S patch cm nest-lab-files --type merge \
  -p '{"data":{"app-config.json":"{\"banner\":\"hot reloaded\",\"rateLimitPerMinute\":1}"}}'

# จอ 2 (Ctrl-C เพื่อหยุด)
while true; do curl -s $STG/config | jq -c .fromFile.data; sleep 3; done

    รอประมาณ 30–60 วินาที (ตอนทดสอบ lab นี้ใช้ ~36 วินาที) ค่าจะเปลี่ยนเองโดย pod ไม่ restart เช็กได้จาก k -n $S get pod ที่ AGE และ RESTARTS ไม่เปลี่ยน

  5. ผู้สอน: ย้ำว่า kubectl patch ใช้เพื่อเรียนเท่านั้น งานจริงแก้ ConfigMap ใน git (kustomize) แล้วให้ CI หรือ Argo CD apply ถ้า patch มือ รอบหน้ามีคน deploy ค่าจะถูกทับคืน

Deploy ไม่ล่ม

ออก version ใหม่ระหว่างมีคนใช้งาน แล้วไม่มี request ไหน error

จอ 2: ยิง request ไม่หยุด
while true; do curl -s -o /dev/null -w '%{http_code} ' $STG/; sleep 0.1; done
  1. build version ใหม่ (จอ 1) 
    docker build --build-arg APP_VERSION=0.2.0 -t localhost:5001/nest-lab:0.2.0 .
docker push localhost:5001/nest-lab:0.2.0

    รอบนี้เร็วเพราะ Docker ใช้ layer ที่ cache ไว้จากภารกิจ 3 ทางลัดคือ make image TAG=0.2.0

  2. ออก version 0.2.0 
    k -n $S set image deploy/nest-lab app=localhost:5001/nest-lab:0.2.0
k -n $S rollout status deploy/nest-lab
curl -s $STG/ | jq .version
    ควรเห็น
    "0.2.0"        จอ 2: 200 200 200 ... ไม่มีตัวอื่นเลย
  3. ดูว่า k8s ทำอะไรไป 
    k -n $S get rs
k -n $S rollout history deploy/nest-lab

    ReplicaSet ของ version เก่าลดเหลือ 0 แต่ยังเก็บไว้ จึงย้อนกลับได้

  4. ย้อนกลับ (rollback) 
    k -n $S rollout undo deploy/nest-lab
k -n $S rollout status deploy/nest-lab
curl -s $STG/ | jq .version
    ควรเห็น
    "0.1.0"
  5. scale มือ แล้วดู HPA เอาคืน 
    k -n $S scale deploy/nest-lab --replicas=4
k -n $S get pod -o wide
k -n $S get hpa -w

    pod 4 ตัวกระจายไปทุก zone แต่ราว 1 นาทีต่อมา HPA จะลดกลับเหลือ 2 เพราะ CPU ต่ำ เมื่อมี HPA แล้ว HPA เป็นคนคุมจำนวน pod ไม่ใช่เรา

  6. ทำไม user ไม่เห็น errorอยู่ตรงไหน
    สร้าง pod ใหม่ก่อน แล้วค่อยปิดตัวเก่าmaxUnavailable: 0
    ส่ง request ให้เฉพาะ pod ที่ตอบ ready แล้วreadinessProbe
    ตัวเก่ารอ 5 วินาทีให้ request ที่ค้างอยู่เสร็จก่อนปิดSHUTDOWN_DELAY_MS

    ตอนทดสอบ lab นี้ยิง 6,123 request ระหว่าง rollout แล้ว error 0 ตัว

    pod ใหม่เป็น CrashLoopBackOff แต่ pod เก่ายัง Running และเว็บยังตอบ 200 เพราะ maxUnavailable: 0 ไม่ปิดตัวเก่าจนกว่าตัวใหม่จะพร้อม

  2. describe pod ที่พัง 
    k -n $S describe pod <pod-ที่-CrashLoopBackOff>

    ดู Last State: Terminated และ Events ท้ายสุด (Back-off restarting failed container) รู้ว่าตายตอน start แต่ยังไม่รู้ว่าทำไม

  3. อ่าน log ของรอบที่ตาย 
    k -n $S logs <pod-ที่-CrashLoopBackOff> --previous
    ควรเห็น
    Invalid SHUTDOWN_DELAY_MS="abc": expected a non-negative integer
  4. แก้ที่ต้นเหตุ 
    k -n $S patch cm nest-lab-env --type merge -p '{"data":{"SHUTDOWN_DELAY_MS":"5000"}}'
k -n $S rollout restart deploy/nest-lab
k -n $S get pod -w

    rollout undo ช่วยไม่ได้ เพราะ pod ทุก version อ่าน ConfigMap ตัวเดียวกันที่พังอยู่ และการลบ pod วนไปมาก็ไม่ช่วย ต้องแก้ config

เจอ pod มีปัญหา ทำตามลำดับนี้

get pod

STATUS อะไร RESTARTS กี่ครั้ง อยู่ node ไหน

describe pod

อ่าน Events ท้ายสุด: ดึง image ไม่ได้ หา Secret ไม่เจอ probe fail

logs --previous

ถ้า RESTARTS มากกว่า 0 สาเหตุมักอยู่ใน log ของรอบที่ตาย

แก้ที่ต้นเหตุ

config, image หรือ resource ไม่ใช่ลบ pod ซ้ำ ๆ

STATUSแปลว่าดูอะไรก่อน
Pendingหา node ลงไม่ได้describe pod ดู Events (resource ไม่พอ, taint)
ImagePullBackOffดึง image ไม่ได้ชื่อ/tag ถูกไหม push แล้วหรือยัง
CreateContainerConfigErrorหา ConfigMap/Secret ไม่เจอdescribe pod บอกชื่อที่หาไม่เจอ
CrashLoopBackOffapp start แล้วตายซ้ำlogs --previous
Running 0/1readiness ไม่ผ่าน ไม่ได้รับ trafficdescribe pod ดู Readiness probe failed

คำถามทบทวน

ลบ pod แล้วทำไมมันกลับมาเอง

Deployment บอกว่าอยากได้ 2 ตัว ReplicaSet เห็นเหลือ 1 เลยสร้างเพิ่ม ถ้าอยากให้หายจริงต้อง scale หรือลบ Deployment

แก้ GREETING ใน ConfigMap แล้วเว็บยังโชว์ค่าเก่า ต้องทำอะไร

rollout restart เพราะ env var ถูกอ่านตอน process เริ่มครั้งเดียว ถ้าเป็น ConfigMap ที่ mount เป็นไฟล์จะเปลี่ยนเองใน ~1 นาที

liveness fail กับ readiness fail ต่างกันยังไง

liveness fail = restart container. readiness fail = เอาออกจาก Service ชั่วคราว pod ยังอยู่

ทำไม rollout แล้ว user ไม่เห็น error

maxUnavailable: 0 สร้างตัวใหม่ก่อนปิดตัวเก่า, readinessProbe ส่ง traffic ให้เฉพาะตัวที่พร้อม และตัวเก่ารอ request ค้างให้เสร็จก่อนปิด

pod เป็น CrashLoopBackOff คำสั่งแรกที่ควรรันคืออะไร

kubectl logs <pod> --previous เพื่อดูว่า container รอบก่อนตายเพราะอะไร แล้วตามด้วย describe pod ดู Events

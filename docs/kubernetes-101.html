เตรียมก่อนวันสอน

ปัญหาที่เจอบ่อยในห้องเรียนไม่ใช่ Kubernetes แต่เป็นเครื่องผู้เรียน เตรียม 4 อย่างนี้ล่วงหน้า

  • Docker Desktop ให้ RAM อย่างน้อย 4 GB (cluster ใช้จริงประมาณ 1.5–2 GB)
  • ให้ผู้เรียนรัน docker compose pull และ make image ที่บ้านก่อน image รวมกันหลายร้อย MB ถ้าดึงพร้อมกันบน Wi-Fi ห้องเรียนจะช้ามาก
  • port ที่ต้องว่าง: 6443 API server, 8080 LB, 8404 LB stats, 5001 registry (macOS ใช้ 5000 กับ AirPlay อยู่แล้ว)
  • ปิด sleep ระหว่างสอน (caffeinate -d บน macOS)
เจอมาแล้วตอนทดสอบ

Mac sleep ระหว่าง lab ทำให้นาฬิกาใน cluster กระโดด ผลคือ API server ตอบ Unauthorized ชั่วคราว rollout ขึ้น exceeded its progress deadline และบาง pod restart เอง ถ้าเห็นอาการแปลก ๆ ให้รัน make stop && make start ก่อนเสียเวลา debug

บทที่ 1

ทำไมต้อง Kubernetes

Docker ตอบคำถามว่า "รัน app 1 ตัวยังไง" แต่ production ต้องตอบคำถามที่ยากกว่า: รันกี่ตัว บนเครื่องไหน ตัวไหนตายแล้วใครเปิดใหม่ ออก version ใหม่ยังไงไม่ให้ user เห็น error และ config ต่างกันต่อ environment ยังไง

Kubernetes แก้ด้วยแนวคิดเดียวคือ desired state เราเขียน YAML บอกว่า "อยากได้ nest-lab 3 ตัว แต่ละตัวมี CPU 100m" แล้ว controller ใน cluster จะวนเช็คตลอดเวลาว่าของจริงตรงกับที่ขอไหม ถ้าไม่ตรงก็แก้ให้ตรง เรียกว่า reconciliation loop

Imperative (สั่งทีละขั้น)

"ssh เข้าเครื่อง B แล้ว docker run อีกตัว" ถ้าเครื่อง B ตายตอนตี 3 ไม่มีใครสั่งให้

Declarative (บอกผลลัพธ์)

replicas: 3 pod ตาย 1 ตัว ReplicaSet controller เห็นว่าเหลือ 2 จึงสร้างใหม่เองภายในไม่กี่วินาที

ผู้สอน · demo 30 วินาที

เปิด kubectl -n nest-lab-prod get pod -w ค้างไว้ แล้วลบ pod 1 ตัวให้ผู้เรียนเห็นตัวใหม่โผล่มาแทนทันที เป็นภาพที่อธิบาย desired state ได้ดีที่สุด

ConfigMap และ Secret

หลักคือ image เดียวกันใช้ได้ทุก environment ส่วนที่ต่างกันอยู่ใน ConfigMap (ค่าทั่วไป) และ Secret (ค่าลับ) lab มี ConfigMap 2 ตัวเพื่อให้เห็นความต่างของการ inject 2 แบบ เปิด /config ดูได้ทั้งคู่

nest-lab-env · inject เป็น env

ค่าถูกอ่านครั้งเดียวตอน container start แก้ ConfigMap แล้ว pod ที่รันอยู่ไม่เห็นจนกว่าจะ rollout restart

nest-lab-files · mount เป็นไฟล์

kubelet อัปเดตไฟล์ให้เองภายในประมาณ 1 นาที app อ่านไฟล์ใหม่ทุก request จึงเปลี่ยนโดยไม่ต้อง restart (ยกเว้น mount ด้วย subPath)

3 วิธีสร้าง ConfigMap

Pattern production: configMapGenerator

ConfigMap ชื่อคงที่มี 2 ปัญหา คือแก้แล้ว pod ไม่ restart และ rollout undo ไม่ย้อน config ให้ Kustomize แก้ด้วยการต่อ hash ของเนื้อหาไว้ท้ายชื่อ เช่น nest-lab-extra-4g86855k5g พอค่าเปลี่ยน ชื่อเปลี่ยน pod template เปลี่ยน Deployment จึง rollout เอง และ ConfigMap ชื่อเก่ายังอยู่ให้ rollback ได้ ตัวอย่างอยู่ที่ k8s/lab/generator/

Secret

  • ค่าใน Secret เป็นแค่ base64 ไม่ได้เข้ารหัส ใครมีสิทธิ์ get secret ก็อ่านได้ ควบคุมด้วย RBAC
  • Secret ที่ inject เป็น env ต้อง restart เหมือน ConfigMap หลัง rotate
  • ถ้า pod อ้าง Secret ที่ไม่มีอยู่ จะค้างที่ CreateContainerConfigError พอสร้าง Secret แล้วจะเดินต่อเอง
  • บน AWS เก็บค่าจริงใน Secrets Manager แล้วใช้ External Secrets Operator sync เข้ามา ไม่ commit Secret ลง git
ผู้สอน · Lab 3.6 ห้ามข้าม

ให้ผู้เรียนใส่ SHUTDOWN_DELAY_MS: "abc" แล้ว restart จะเห็น pod ใหม่ CrashLoopBackOff แต่ curl ยังได้ 200 เพราะ maxUnavailable: 0 ทำให้ pod เก่าไม่ถูกปิดจนกว่าตัวใหม่จะ ready เป็นบทเรียนที่ทำให้คนเห็นคุณค่าของ rolling update ทันที

ความผิดพลาดยอดฮิต

อย่าให้ liveness เช็ค database ถ้า DB สะดุด 10 วินาที liveness จะ fail พร้อมกันทุก pod แล้ว kubelet restart ทั้งหมดในคราวเดียว ทำให้ระบบล่มหนักกว่าเดิม

เกิดอะไรขึ้นตอน pod ถูกปิด

จุดที่คนส่วนใหญ่ไม่รู้คือ Kubernetes ถอด pod ออกจาก endpoint พร้อมกับส่ง SIGTERM ไม่ได้ถอดก่อน ถ้า app ปิดทันที request ที่ load balancer ยังส่งมาจะ error

  1. t = 0

    Deployment สั่งลบ pod เก่า สถานะเป็น Terminating

  2. t = 0

    2 อย่างเกิดพร้อมกัน: endpoint controller เริ่มถอด pod ออกจาก Service และ kubelet ส่ง SIGTERM ให้ container

  3. 0 – 5 s

    NestJS รับ SIGTERM แล้วให้ /health/ready ตอบ 503 แต่ยังเสิร์ฟ request ต่อ รอ SHUTDOWN_DELAY_MS=5000 ให้ทุกจุดอัปเดตตาม

  4. 5 s

    app.close() ปิด HTTP server หลังจบ request ที่ค้าง แล้ว process exit

  5. 30 s

    ถ้ายังไม่ exit จะโดน SIGKILL ตาม terminationGracePeriodSeconds: 30

บทที่ 7

Scale และทนต่อการพัง

  • requests คือสิ่งที่ scheduler ใช้จอง node และ HPA ใช้คิด % CPU ส่วน limits คือเพดาน memory เกิน limit จะโดน OOMKilled
  • HPA ปรับจำนวน replica ตาม CPU เฉลี่ยเทียบกับ request (lab ตั้งเป้า 70%)
  • topologySpreadConstraints กระจาย pod ไปทุก zone เพื่อให้ AZ เดียวล่มแล้วยังเหลือ pod ใน zone อื่น
  • PodDisruptionBudget จำกัดว่าตอน drain node หรือ upgrade node group ปิด pod ได้ทีละกี่ตัว

Timeline เมื่อ worker ทั้งเครื่องหาย (Lab 10)

  1. t = 0

    docker compose stop worker-1b จำลอง AZ ล่ม

  2. ~4 s

    LB health check ถอด worker-1b (ดูได้ที่ localhost:8404)

  3. ~40–50 s

    node ขึ้น NotReady ช่วงนี้ Traefik ยังอาจส่ง request ไปหา pod บน node ที่ตาย จึงมี error บางส่วน

  4. +30 s

    เกิน tolerationSeconds: 30 (ค่า default จริงคือ 300) pod ถูก evict และสร้างใหม่ใน zone ที่เหลือ

  5. ภายหลัง

    เปิด worker-1b กลับมา pod ไม่ย้ายกลับเอง ต้อง rollout restart หรือใช้ descheduler

บทที่ 11

คำถามทบทวน

ใช้ท้ายแต่ละช่วงหรือปิด workshop กดที่คำถามเพื่อดูคำตอบ

แก้ ConfigMap ที่ใช้ envFrom แล้ว ทำไม app ยังเห็นค่าเดิม

env ถูกอ่านครั้งเดียวตอน container start ต้อง rollout restart หรือใช้ configMapGenerator ที่เปลี่ยนชื่อตาม hash เพื่อให้ rollout อัตโนมัติ

readiness กับ liveness ต่างกันอย่างไร

readiness fail จะถอด pod ออกจาก Service แต่ไม่ restart ส่วน liveness fail จะ restart container จึงห้ามให้ liveness ขึ้นกับระบบภายนอกอย่าง database

ทำไม app ต้องรอ SHUTDOWN_DELAY_MS ก่อนปิด

Kubernetes ส่ง SIGTERM พร้อมกับเริ่มถอด endpoint ไม่ได้ถอดก่อน ถ้าปิดทันที request ที่ load balancer ยังส่งมาจะ error

Pod อยู่ Pending นาน ดูอะไรก่อน

kubectl describe pod ดู Events ล่างสุด มักเป็น Insufficient cpu, taint ที่ไม่ได้ tolerate หรือ PVC ที่ยัง bind ไม่ได้

Secret ปลอดภัยเพราะเป็น base64 ใช่ไหม

ไม่ใช่ base64 ถอดได้ทันที ความปลอดภัยมาจาก RBAC, encryption at rest (KMS บน EKS) และการไม่ commit ค่าจริงลง git

HPA คิด % CPU จากอะไร

จาก resources.requests.cpu ไม่ใช่ limit ใน lab request คือ 100m ถ้า pod ใช้ 70m ถือว่า 70%

Node ตายแล้ว pod ย้ายไปเมื่อไหร่

หลัง node ถูก mark NotReady (~40–50 วินาที) แล้วรออีก tolerationSeconds ซึ่ง default คือ 300 วินาที ใน lab ตั้งไว้ 30

maxUnavailable: 0 ช่วยอะไรตอน config พัง

pod เก่าจะไม่ถูกปิดจนกว่า pod ใหม่จะ ready ถ้าตัวใหม่ crash rollout จะค้างแต่ระบบยังให้บริการจาก pod เก่าได้ครบ
